# Decisions

Choices made where the spec is silent. Simplest option wins; each is noted here.

## Step 1: shell

- **Spec file name.** The spec lives at `Clotting Cascade Mastery App — Spec.md`, not `SPEC.md`. Left as is.
- **Framework.** Vite + Preact (plain JSX, no TypeScript). Smallest component framework that keeps the UI manageable; no server.
- **PWA.** `vite-plugin-pwa` (Workbox) generates the service worker and precaches every built file, so the app works offline after first load. Updates install automatically on next launch.
- **Routing.** Hash routes (`#/home`, `#/learn`, …) so GitHub Pages never needs server rewrites.
- **IndexedDB wrapper.** `idb` (tiny promise wrapper). All Phase 1 stores are created in DB version 1.
- **Dark mode before first paint.** The setting lives in IndexedDB; a copy is mirrored to `localStorage` only so `index.html` can apply it before the first frame. Progress never goes to localStorage.
- **Icons.** Generated by `scripts/make-icons.mjs` (red drop on dark square), no image tooling needed.
- **Install walkthrough.** Shown on first visit in a browser tab, never inside the installed app. iPhone gets a 4-step Share → Add to Home Screen walkthrough; Android/desktop Chrome get the native Install button.
- **No disclaimer text.** Devin asked (2026-10-30) for zero disclaimers. The spec's "study tool, not a clinical reference" line was removed. The one status label kept is "Unverified: written by the app, not yet reviewed" on app-written definitions, because it tells the learner which text was never checked.
- **Repo.** Public GitHub repo `clotting-cascade` (Pages on a free account needs public). Deploys from `main` via `.github/workflows/deploy.yml`; `npm run build` runs the tests first, so a failing test blocks deploy.

## Steps 2–5: content and app

- **Content layout.** One folder per module (`content/m1/`) holding the spec's six files. The app loads every `content/m*/*.json` it finds at build time.
- **Source registry.** Sources live once in `content/sources/index.json` (title, URL, accessed date, how fetched). Each claim source is `{ref, passage}`, and the passage is the exact quoted text. Tests fail if a ref is missing.
- **Fetching.** NCBI Bookshelf (StatPearls) answers scripts with a CAPTCHA page, which I did not try to bypass. Those pages were read in the in-app browser, and every quoted passage was later re-checked word for word against the live page. OpenStax, DailyMed, and the PMC vWF review were fetched by script and saved to `content/sources/<id>.txt`.
- **"Two sources" means two different documents.** Two passages from the same article count as one source.
- **Edge relations.** The spec lists activates / inhibits / requires / cleaves / tracks. Primary hemostasis also needs **binds**, **releases**, and **produces** (vWF binds collagen, dense granules release ADP, COX-1 produces TXA2), so these three were added.
- **Drug nodes in Module 1.** Aspirin, clopidogrel, prasugrel, and ticagrelor appear only for their antiplatelet mechanism and duration, because Module 1 must cover COX-1 and P2Y12. Indication, lab, reversal, and EMS notes wait for Module 6, and each drug card says so.
- **Questions cite claims.** Questions carry `claims[]` (ids of the node claims they rest on) instead of repeating sources.
- **Flashcards.** One card per node claim. The writer sets the front (`card_front`) and the back is the claim text. `scripts/build-content.mjs` regenerates `cards.json` and `excerpts.md`, and a test fails if `cards.json` is stale.
- **Glossary underlines.** Every glossary term and alias is underlined automatically wherever it appears. `[[term]]` markup is used only where the word form differs from the entry ("irreversibly"); the build test checks every `[[...]]` has an entry.
- **Unverified definitions.** The app can't write definitions offline, so `content/unverified.json` holds short app-written definitions for technical words in the content that have no verified entry. The Define button shows one when it exists, always labeled. Otherwise it shows "No quick definition yet" plus StatPearls and DailyMed search links. Either way the term goes on the define list.
- **Study day boundary at 04:00**, so a 0300 session counts toward the shift it belongs to.
- **Graded schedule.** Pass 2 opens 2+ days after pass 1, and pass 3 opens 6+ days after pass 2 (each gap counted from the previous pass).
- **Prerequisites.** A goal's quizzes unlock once each prerequisite has one graded pass, not full mastery, which would block for 8+ days.
- **Pre-test pending.** Goals in a module whose pre-test hasn't been taken or skipped show "Pre-test pending" but can still be quizzed; nothing is gated. The pre-test asks the first question of each listed goal.
- **Leaving Review.** A graded pass on a goal in Review restores it. If it had 3 passes it returns to Mastered, and the 30/90-day retention clock restarts from that day.
- **Corrections.** `content/corrections.json` lists corrected claims as `{id, date, nodes, note}`. On load, every started goal covering those nodes drops to Review with the note. A goal that was never attempted is untouched.
- **Retention checks** leave out tap-the-diagram items (the spec says no diagram), and show no glossary underlines or explanations.
- **Catch-up.** It triggers when the app opens after one or more missed days with overdue reviews. Each day's share is `ceil(pile at start of day ÷ days left)`.
- **Shift day.** No new cards, reviews capped at the shift minimum, graded quizzes, re-checks and retention checks hidden until the next day. Nothing is penalized because none of them have deadlines.
- **Order questions** are answered by tapping steps in sequence (tap a placed step to take it back). This is more reliable on a phone than drag-and-drop. Drag-and-drop arrives with the Builder in Phase 4.
- **Diagram edges** bend around boxes they would otherwise cross.
- **Export** uses the iOS share sheet when it can share files, otherwise a download. The file holds every IndexedDB store, the define list, glossary taps, and "I was right" overrides.
